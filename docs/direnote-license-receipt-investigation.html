DireNote's CONTENT_INGESTION endpoint nevertheless returns an HTTP 200 response containing the text “Failed to upload license receipt”, instead of its documented JSON result. The remaining failure is in DireNote's receipt-import/storage path or an undocumented provider-side URL policy.

2. DireNote contract and observed behavior

DireNote API v2.2 documents license_receipt_url as conditionally required for Non-Exclusive Licensed content and describes it as a public PDF URL. It does not document a Google Drive-only requirement, a special host requirement, or an authenticated upload flow.

The documented successful ingestion response is JSON with success: true, UPC, track information and warnings. The observed response is neither JSON nor a documented error response despite using HTTP 200.

4. HYMN implementation safeguards

  • Proof links are public to DireNote but unguessable: the URL contains a server-generated provider token and requires no HYMN account session.
  • Asset reads are backed by persistent Hostinger storage, not a deployment directory or Vercel storage.
  • Responses send Content-Type: application/pdf, a PDF filename, byte length, range support, and Cache-Control: public.
  • HYMN preserves failed attempts and prevents duplicate ingestion during an active submission.
  • HYMN now classifies this provider response as DIRENOTE_LICENSE_RECEIPT_IMPORT_FAILED, rather than incorrectly treating it as a generic malformed response.

5. Required DireNote investigation

  1. Locate the ingestion request for the account and release details above in DireNote logs.
  2. From the same DireNote worker that imports receipts, fetch the supplied license_receipt_url and record: DNS result, TLS result, HTTP status, final URL after redirects, MIME type, byte count, and body hash.
  3. Inspect the subsequent receipt-save/upload operation. The text specifically says “Failed to upload license receipt”, which suggests a failure after URL retrieval (for example provider storage, quota, service-account permissions, or an unhandled upload exception).
  4. Check any outbound-host allowlist, WAF, IPv4/IPv6 egress, TLS-certificate validation, maximum file-size, and PDF parser constraints that could reject a valid 101 KB HTTPS PDF.
  5. Return a machine-readable JSON error with a non-2xx HTTP status when the receipt import fails. Include a stable error code and safe diagnostic reason.
