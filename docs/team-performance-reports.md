# Team OS performance reports

Active employees receive a daily report at 23:59 Asia/Kolkata and a weekly report on Monday at 09:00 for the previous Monday–Sunday. Owners supervise and do not receive employee quota emails. All active members can open their own live report at `/team/performance`; viewing another member requires `reports.all.view` or workspace owner access. Team OS includes a My performance link and a report entry in Weekly Reports.

The dedicated authenticated `team-performance` cron is registered at a 60-second cadence in Hostinger's runtime scheduler and Vercel cron configuration, and in the existing GitHub frequent-job fallback. Delivery occurs on the first available scheduler run at or after the configured time; outages and SMTP latency can delay it. The GitHub fallback has a five-minute cadence. A latest-due daily report and latest completed weekly report are caught up without a bulk historical backfill. Existing `TEAM_AUTOMATION_ENABLED=false` pauses generation and delivery. Normal transactional SMTP configuration is reused.

Reports include registered and currently contactable leads, distinct contacted prospects, contact attempts, replies, attributed customer conversions, completed assignments, role-specific targets, prior-period comparisons, daily breakdowns, outstanding follow-ups/tasks and evidence-based coaching. They do not infer attendance, leave, hours worked or personal effort. Researcher and caller targets use current role preferences and the existing calendar-day CRM programme. Pre-membership days are excluded. Generic roles have no invented lead quota. Draft outreach does not count. Multiple contacts with the same prospect count once per report period.

Commission uses the employee acquisition ledger, not artist royalty accounts or estimates. New EARNED entries, signed adjustments and net entries are separated by currency. The hold, unallocated-cleared and payout-allocated amounts describe only entries created in the report period, not the all-time withdrawable balance. Payout allocation is not bank-payment confirmation. Refund adjustments can make amounts negative. Current ledger eligibility, allocation and lead verification are evaluated at capture time. Current follow-up/task queues are not reconstructed historical queues.

Daily emails are snapshots captured at approximately 23:59, not a promise to include the final minute or later backdated entries. The exact cutoff is displayed in email and web reports. A live daily/weekly report reflects subsequent records and corrections; an emailed snapshot stays unchanged. Earlier full periods are compared as full periods, with a partial-period caveat for live reports.

Each report is persisted in existing `email_logs` as template `team_performance_report`, channel `team_performance`, with a unique member/period/start-date event key. Its structured snapshot and rendered email are committed together with an in-app notification. No database migration or new provider is needed. Disabling SMTP retains pending snapshots and web access; it does not record a successful send. Existing sent emails are never rewritten. Mail links lead to protected `/team/performance/<email-log-id>` pages; JSON downloads repeat the same active-membership and workspace-scoped permission checks. No public token grants report access. Login return paths allow only explicit report paths, excluding arbitrary external redirects.

The outbox atomically claims pending rows, rechecks active membership, employee role, active user and unchanged recipient before SMTP, and prevents parallel workers from sending the same claimed email. Confirmed pre-connection failures receive bounded backoff. Uncertain SMTP outcomes or stale claims become `review` and require delivery investigation before resend. Historical snapshot data is preserved. SMTP cannot guarantee exactly-once delivery after a provider acceptance followed by process failure; uncertain cases are never automatically resent.

Verification:

- `node --import tsx scripts/verify-acquisition-isolated.ts --performance-only` uses a disposable loopback PostgreSQL database with SMTP disabled and a fake delivery function; production accounts and recipients are untouched.
- `node scripts/verify-team-performance-browser.cjs` checks the actual report component at desktop and mobile sizes.
- TypeScript and targeted ESLint cover the new services, pages, email template and scheduler changes.

Design references: [Salesforce dashboard metrics](https://www.salesforce.com/sales/analytics/sales-dashboard-examples/) and [HubSpot sales reporting](https://knowledge.hubspot.com/reports/create-sales-reports-in-the-sales-analytics-suite). The implementation uses recorded activity and clearly defined outcomes rather than an invented productivity score.
