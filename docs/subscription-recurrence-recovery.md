# Annual subscription UPI recovery

The November 3 investigation of a Yearly+ checkout found a correct INR 199,900 minor-unit annual plan and an unstarted `created` subscription. The customer's UPI app reported `validateRecurrencePatternRuleValue-"YEARLY"-recurrenceValue`; the gateway retained a failed UPI authentication with no paid subscription cycle. The app's detailed yearly-rule rejection is not reproduced in the gateway's generic cancellation description, so successful bank authorization still requires the customer to retry.

New annual checkouts use a verified equivalent `monthly` period with interval `12`, keeping the full annual price and 12-month billing cadence. This uses the gateway's documented custom-frequency/as-presented mandate path rather than the rejecting YEARLY rule. It does not create monthly charges or change annual entitlements. Reference: [Razorpay Create a Plan](https://razorpay.com/docs/api/payments/subscriptions/create-plan/).

`scripts/prepare-subscription-recurrence.ts --product=yearly_plus --source-plan=<verified-id>` previews the exact price/currency and schedule. `--apply` creates/reuses a plan template, persists a plan version and registers its source mapping in the existing audit ledger. It never creates a customer subscription or payment. Both provider notes and current pricing/cadence are checked at checkout; missing or malformed mappings fail closed. Previously active subscriptions retain their existing provider plan and lifecycle.

On an explicit customer retry, a legacy created annual mandate can be retired only when it has zero paid/authenticated cycles, no local payment entries, unpaid invoices, exclusively failed linked payments older than five minutes, and freshly confirmed unchanged provider state. Bounded reads with incomplete evidence, recent/in-flight payments, authorization or active subscriptions prevent replacement. Cancellation must be confirmed before a new mandate can be created. The prior ID, source plan and reason remain in audit evidence. Delayed creation/cancellation webhooks for that verified retired ID are acknowledged without changing the replacement; unexpected money on it remains an error requiring review.

A customer-row transaction lock serializes simultaneous checkout requests. A separate durable create intent survives a provider timeout or database rollback. A retry with an unresolved intent is blocked for reconciliation instead of silently creating a second mandate. Explicit provider rejections are recorded separately; successful persistence commits a matching completion marker. Provider creation remains an authorization request, not a claimed successful payment. Existing signature, ownership, price, capture and webhook entitlement checks remain in place.

Verification: `verify-subscription-recurrence.ts`, `verify-subscription-checkout-resume.ts`, `verify-subscription-plan-validation.ts`, `verify-razorpay-subscriptions.ts`, and `verify-acquisition-isolated.ts --subscription-recurrence-only`. These cover annual price/cadence, bad mappings, billing-cycle limits, duplicate browser requests, active/paid/recent payment protection, ambiguous responses and delayed retired-ID webhooks. Gateway tests are mocked; the concurrency/recovery suite uses disposable PostgreSQL with no live payments or customer contact.
